spinal-fleet is how Spinal runs one private copy of the product per enterprise customer,
inside that customer's own Azure subscription. We operate it from our GCP project through
[Azure Lighthouse](https://learn.microsoft.com/azure/lighthouse/), and we never hold a
credential in the customer's tenant.

## How it works, in one paragraph

Everything we choose about a customer lives in one folder in the `spinal-fleet` repo.
Merging a change to `main` builds an image that contains the repo and points a Cloud Run
Job at it. Pressing a button runs that job for one customer: it creates or updates
everything the customer needs, in their Azure and on our side, then checks the site
answers. Every step is safe to re-run, so a first launch, a release, and a retry after a
failure are all the same button. Offboarding is the same job in reverse.

## One folder per customer

`customers/<slug>/` is the customer's operational record. Four files:

| File | Contents |
|------|----------|
| `target.env` | Declared facts: the delegated subscription id, the Auth0 org id and domains |
| `params.bicepparam` | Every template parameter, including the image pins |
| `env.schema` | Key names in the composed env blob, no values |
| `manifest.md` | Facts, dates, status, and the closing record at offboarding |

<Warning>
No secret values in the repo, ever. Secrets live in GCP Secret Manager and in the
customer's own Key Vault. The repo stores names, pointers, and version pins only.
</Warning>

## The slug

The folder name is the slug. It becomes the public hostname
`dashboard.<slug>.withspinal.com` and every resource name in every system, so treat it as
permanent. Lowercase letters and digits, twelve characters at most; the reasons are in
[Naming limits](/fleet/naming-limits).
