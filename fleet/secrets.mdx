All secret values live in GCP Secret Manager in the fleet project for the tier
(`spinal-454720` for test, `spinal-production-502715` for customers). The repo and these
docs hold names and pointers only, never values.

There are two kinds: six fleet-level secrets a human stages once, and per-customer secrets
the launch mints itself. The readiness gate checks that all six fleet secrets exist before
any launch is approved.

## Fleet-level secrets (staged once, held by no human afterwards)

There are six of these. A person stages each one once, and after that only the control plane reads them.

| Secret | Purpose |
|--------|---------|
| `fleet-temporal-api-key` | Temporal Cloud API key for the admin user. The control plane uses it for account-level work only: creating a customer namespace, creating the namespace-scoped service account, and minting that account's key. It never leaves the control plane. |
| `fleet-cloudflare-token` | Cloudflare API token. Used by `ensure_tls_cert` for DNS-01 certificate validation and by `ensure_dns_record` to upsert the customer's A record on `withspinal.com`. |
| `fleet-auth0-provisioning-client-secret` | Client secret of the Auth0 provisioning M2M app (broad tenant scopes: create clients, read client keys, update connections). Pairs with `FLEET_AUTH0_PROVISIONING_CLIENT_ID` in worker config. Control plane only; never enters a customer environment. See [Auth0](/fleet/auth0). |
| `fleet-auth0-mgmt-client-secret` | Client secret of the Auth0 runtime M2M app (org-invitation scopes only). Pulled into every composed customer env as `AUTH0_MGMT_CLIENT_SECRET`; the backend uses it to send invitations. Pairs with `AUTH0_MGMT_CLIENT_ID` in each customer's target.env. |
| `fleet-logfire-token` | Logfire observability token. Pulled into the composed env as `LOGFIRE_TOKEN`. |
| `fleet-sentry-dsn` | Sentry DSN. Pulled into the composed env as `SENTRY_DSN`. |

<Note>
`fleet-auth0-client-secret` (the shared login app's secret) predates the per-customer app
model and is no longer read by anything. Login-app secrets are now minted per customer.
</Note>

## Per-customer secrets (minted by the launch)

All are named `<slug>-<suffix>` and labelled `customer=<slug>`.

| Secret | Minted by | Purpose |
|--------|-----------|---------|
| `<slug>-env` | `ensure_customer_env` | The customer's complete chosen config surface, composed from generated values, fleet-pulled secrets, the minted app identity, and slug-templated URLs. Contains the generate-once trio: `DB_PASSWORD` (what Postgres was created with), `SESSION_SECRET_KEY`, and `TOKEN_ENCRYPTION_KEY` (a Fernet key; regenerating it bricks encrypted rows). Never deleted or re-composed once the stack exists; config changes are new versions. |
| `<slug>-auth0-client-secret` | `ensure_auth0_app` | Client secret of the customer's own login application `dashboard-<slug>`. Read back during env composition as `AUTH0_CLIENT_SECRET`. |
| `<slug>-gcp-sa-key` | `ensure_service_account` | JSON key of `registry-reader-<slug>`, the SA with read access to the `dashboard` Artifact Registry repo. Azure Container Apps use it to pull images. |
| `<slug>-gcp-runtime-key` | `ensure_runtime_service_account` | JSON key of `app-runtime-<slug>`, the backend's Google SDK identity (Vertex AI, Document AI, Translation, Flipt ID tokens). Mounted in the container at `/gcp-sa/key.json` via `GOOGLE_APPLICATION_CREDENTIALS`. |
| `<slug>-temporal-api-key` | `ensure_temporal_namespace` | API key of the namespace-scoped Temporal Cloud service account `<slug>-worker`, with Write on that customer's namespace only. The only Temporal credential that ever exists inside a customer environment. |
| `<slug>-tls-cert` | `ensure_tls_cert` | The Let's Encrypt certificate for `dashboard.<slug>.withspinal.com` as a base64 PFX, the format Application Gateway consumes. Reissued when fewer than 30 days remain. |

## GCP service accounts and their grants

The two per-customer keys above belong to service accounts the launch mints. Their IAM
grants, as the worker code creates them:

**`registry-reader-<slug>@<project>.iam.gserviceaccount.com`** (minted by
`ensure_service_account`)

| Role | Scope |
|------|-------|
| `roles/artifactregistry.reader` | the `dashboard` Artifact Registry repository in `europe-west2` only, not the project |

Read-only, and bound at the repository rather than the project, so the credential can pull
images and nothing else.

**`app-runtime-<slug>@<project>.iam.gserviceaccount.com`** (minted by
`ensure_runtime_service_account`)

| Role | Scope |
|------|-------|
| `roles/aiplatform.user` | project (Vertex AI calls) |
| `roles/documentai.apiUser` | project (Document AI OCR) |
| `roles/cloudtranslate.user` | project (Translation API) |
| `roles/run.invoker` | the Flipt feature-flag Cloud Run service only |

The `run.invoker` grant is skipped with a logged warning when `FLEET_FLIPT_RUN_SERVICE` is
unset; the app then reads safe flag defaults.

Grants deliberately absent from the runtime account: VAT service invoker (service
deprecated; VAT lookups raise on Azure by design), Pub/Sub (auto-off on Azure), Cloud
Storage (Document AI runs on bytes, not GCS paths), and Vector Search (dead config).

## How secrets reach the customer environment

At deploy time the worker exports the minted values as environment variables, the
customer's `params.bicepparam` reads them with `readEnvironmentVariable(...)`, and the
template writes them into the customer's Key Vault through the ARM control plane. Secret
values never appear in workflow payloads or on disk outside a private tempdir.

## Conventions

The following rules apply to every secret, whether fleet-level or per-customer.

- Every secret is versioned. Old versions are disabled, never deleted; rollback is a
  version pin.
- Per-secret IAM, with Data Access audit logs on.
- Rotation is `gcloud secrets versions add`, followed by the config-roll flow (PR bumping
  the pin, then the sync workflow).
