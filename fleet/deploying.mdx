Two steps, kept deliberately apart. Merging to `main` prepares and changes no customer.
Pressing the button deploys one customer. Everything runs inside GCP as the fleet identity.

```
 you                          GitHub Actions                       GCP
 ───                          ──────────────                       ───
 merge a PR to main  ──────▶  toolbox.yml
                              • worker tests
                              • build toolbox image @ sha  ──────▶ Artifact Registry  fleet/toolbox:<sha>
                              • gcloud run jobs replace    ──────▶ Cloud Run Jobs  fleet-deploy, fleet-offboard

 Actions ▶ Deploy customer
 pick a slug ▶ Run   ──────▶  deploy.yml
                              • wait for reviewer (if set)
                              • gcloud run jobs execute    ──────▶ fleet-deploy --args=<slug>
                              • stream the job log                    as fleet-worker:
                                                                      readiness → auth0 → env → identities
                                                                      → cert → ARM deploy → DNS → smoke test
                                                                            │
                                                                            ▼
                                                                   the customer's Azure subscription
                                                                   (through Lighthouse)
```

## To ship a new build

These are the five steps. The first three prepare, the last two deploy and confirm.

1. Find the image tags in the Cloud Console under **Artifact Registry** → `dashboard` →
   `backend` and `frontend`: open the image tagged `latest` and copy its sha tag. Never pin
   `latest` itself. If you prefer a command:

   ```bash
   gcloud artifacts docker images list \
     europe-west2-docker.pkg.dev/spinal-454720/dashboard/backend \
     --include-tags --filter="tags~latest" --format="value(tags)"
   gcloud artifacts docker images list \
     europe-west2-docker.pkg.dev/spinal-454720/dashboard/frontend \
     --include-tags --filter="tags~latest" --format="value(tags)"
   ```

2. Set `imageTag` and `frontendImageTag` in `customers/<slug>/params.bicepparam`.
3. Open a PR and merge it. You should see the "Toolbox image" workflow go green. Until it
   does, the merged pins are not deployable: the button always runs what `main` last rolled.
4. **Actions** → **Deploy customer** → **Run workflow**, type `<slug>`, and run it.
   Approve if the environment asks. Without GitHub, use **Cloud Run** → **Jobs** → `fleet-deploy` →
   **Execute** → **Execute with overrides** with `<slug>` as the only argument, or:

   ```bash
   gcloud run jobs execute fleet-deploy \
     --region europe-west2 --project spinal-454720 --args=<slug> --wait
   ```

5. Watch the log. On an existing customer the minting steps skip and the run takes about
   five minutes, most of it the ARM deployment rolling new Container App revisions. It
   ends with `smoke-test done` and `deploy <slug> OK`.

## Other kinds of change

The steps are the same; only the PR differs.

| You want to | The PR | After it goes green |
|---|---|---|
| Change the infrastructure template | edit `infra/azure/*.bicep` | deploy each customer you want on it, one at a time |
| Change the worker or the identity code | edit `worker/` | nothing; the next deploy uses it |
| Roll a config value | add a new Secret Manager version of `<slug>-env`, no PR needed | deploy that customer; the run re-seeds the vault and restarts the apps |
| Change the job itself, such as timeout or memory | edit `infra/gcp/*.job.yaml` | nothing; the push replaced the job |
| Add a customer | see [Launch a customer](/fleet/new-customer) | deploy the new slug; the first run is the launch |

## When it fails

The log names the stage that failed and the error after it. Fix the cause and press the
button again; every step is safe to re-run and completed stages skip. Details on retries,
timeouts, and what each stage does on a re-run are in
[Deploy job internals](/fleet/deploy-job).

The compose stack on a laptop runs the same steps for developing the worker. It is the
[dev loop](/fleet/dev-loop), never the way a customer is deployed.
